# 卡牌效果系统设计文档

## 一、现状分析

### 1.1 当前系统如何工作

项目已有一套完整的"道具→效果"流程，不依赖卡牌 UI，走的是物品栏 (itemSlot0 / itemSlot1) + ServerRpc 的网络通路：

```
玩家从 ItemBoxCounter 获取道具
    ↓ 存入 Player.itemSlot0 / itemSlot1 (NetworkVariable<int>，存的是 SO 在列表中的索引)
    ↓
玩家选择槽位 + 瞄准/选中目标
    ↓
Player.UseItemServerRpc(slotIndex, aimPosition, counterRef)
    ↓ 服务器根据索引从 SabotageItemListSO 取出 SabotageItemSO
    ↓ 根据 targetType 分流：
    ├── Player → Physics.OverlapSphere 找目标 → PlayerEffectHost.ApplyEffect()
    ├── Counter → 从 counterRef 取 CounterEffectHost → ApplyEffect()
    └── Self → 清除自身所有效果 + CleanWipe 闪光
    ↓
效果生效（NetworkVariable<float> 计时器，服务端权威，自动同步客户端）
    ↓
PlayerEffectVisual / CounterEffectHost 读取计时器，驱动视觉效果
```

### 1.2 关键数据结构

| 类 | 作用 | 关键字段 |
|---|---|---|
| `SabotageItemSO` (ScriptableObject) | 定义单种道具的静态数据 | `itemName`, `effectType`, `rarity`, `targetType`, `duration`, `icon` |
| `SabotageItemListSO` (ScriptableObject) | 道具列表，提供索引↔SO 转换 | `List<SabotageItemSO>` |
| `EffectType` (enum) | 效果类型 | `Stun`, `ReverseControls`, `LockCounter`, `CleanWipe` |
| `Rarity` (enum) | 稀有度 | `Common`, `Rare`, `Epic` |
| `TargetType` (enum) | 目标类型 | `Player`, `Counter`, `Self` |
| `PlayerEffectHost` | 玩家效果宿主 (NetworkBehaviour) | stunTimer, reverseTimer, recentVictimTimer |
| `CounterEffectHost` | 台面效果宿主 (NetworkBehaviour) | lockTimer |
| `EffectCardUI` | 卡牌 UI 组件 | CardId, name, description |
| `CardInfo` (struct) | 卡牌信息快照 | cardId, name, description |

### 1.3 现有系统中的三个枚举

```
EffectType:  Stun | ReverseControls | LockCounter | CleanWipe
Rarity:      Common | Rare | Epic
TargetType:  Player | Counter | Self
```

### 1.4 当前卡牌 UI 与效果系统之间的断层

目前 `EffectCardUI` 只是一个空壳 UI：

- 有 `CardId`（纯自增编号，不是 SO 索引）
- `GetCardInfo()` 只返回 UI 上的文本，不包含任何游戏逻辑数据
- `TogglePanelUI.AddCard()` 只是 `Instantiate` 一个空白 prefab，没有关联任何 `SabotageItemSO`
- 卡牌被拖拽消除后，没有任何逻辑回调

**核心问题：卡牌 UI 完全不知道它代表哪张道具 SO，也无法触发道具效果。**

---

## 二、设计目标

1. 每张卡牌关联一个 `SabotageItemSO`（效果数据）
2. 卡牌 UI 能展示 SO 中的数据（名称、描述、图标、稀有度颜色等）
3. 拖拽消除卡牌时，能触发对应的道具效果（替代现有的"选槽位+按使用键"流程）
4. `TogglePanelUI` 能管理卡牌的生命周期，并对外暴露完整的卡牌信息
5. 保持与现有网络架构的兼容（ServerRpc，服务端权威）

---

## 三、设计方案

### 3.1 方案概述：复用 SabotageItemSO + 扩展 EffectCardUI

**核心思路：不新建 SO 类型，直接复用现有的 `SabotageItemSO`。**

理由：

- `SabotageItemSO` 已经包含了卡牌所需的所有信息（名称、效果、稀有度、图标）
- 网络同步已经基于 `SabotageItemListSO` 的索引机制，不需要新的序列化方案
- `Player.UseItemServerRpc` 已经实现了完整的效果执行逻辑，卡牌系统只需要调用它

### 3.2 数据结构变更

#### CardInfo 扩展

```csharp
public struct CardInfo {
    public int cardId;              // 卡牌唯一编号（不变）
    public int itemIndex;          // SabotageItemSO 在 SabotageItemListSO 中的索引（新增）
    public string name;            // 道具名称（从 SO 读取）
    public string description;     // 道具描述（从 SO 生成）
    public EffectType effectType;  // 效果类型（新增）
    public Rarity rarity;          // 稀有度（新增）
    public TargetType targetType;  // 目标类型（新增）
}
```

#### EffectCardUI 新增字段与方法

```csharp
private int itemIndex = -1;  // SabotageItemSO 的列表索引，-1 = 未绑定

public void SetCardData(int id, int itemIndex, SabotageItemSO itemSO) {
    CardId = id;
    this.itemIndex = itemIndex;
    // 用 SO 数据填充 UI
    nameText.text = itemSO.itemName;
    descriptionText.text = GenerateDescription(itemSO);
    iconImage.sprite = itemSO.icon;
    // 根据稀有度设置边框颜色等
    ApplyRarityVisual(itemSO.rarity);
}
```

#### TogglePanelUI 新增字段与方法

```csharp
[SerializeField] private SabotageItemListSO sabotageItemListSO;  // 道具列表引用

// AddCard 改为接收 itemIndex
public EffectCardUI AddCard(int itemIndex) {
    GameObject cardGo = Instantiate(cardPrefab, cardContainer);
    EffectCardUI card = cardGo.GetComponent<EffectCardUI>();
    SabotageItemSO itemSO = sabotageItemListSO.GetFromIndex(itemIndex);
    card.SetCardData(nextCardId++, itemIndex, itemSO);
    return card;
}
```

### 3.3 类之间的数据传递

```
SabotageItemListSO (ScriptableObject, Inspector 配置)
    ↓ GetFromIndex(itemIndex)
SabotageItemSO (静态数据: 名称、效果、稀有度、图标)
    ↓ 传入
TogglePanelUI.AddCard(itemIndex)
    ↓ SetCardData(id, itemIndex, itemSO)
EffectCardUI (持有 itemIndex + 展示 SO 数据)
    ↓ GetCardInfo()
CardInfo (结构体快照: id + itemIndex + 所有字段)
```

**网络层面不变：**

- `Player.UseItemServerRpc(slotIndex, aimPosition, counterRef)` 的签名不变
- 卡牌系统只是另一种"触发使用道具"的入口
- 卡牌的 `itemIndex` 可以直接映射到 Player 的 itemSlot

### 3.4 拖拽消除 → 触发效果

现有 `Player.UseItemServerRpc` 需要 `slotIndex`，但卡牌系统不使用槽位概念。有两个方案：

#### 方案 A：卡牌使用独立的 ServerRpc（推荐）

在 `Player` 中新增一个不依赖槽位的 ServerRpc：

```csharp
// Player.cs 新增
[ServerRpc(RequireOwnership = false)]
public void UseCardServerRpc(int itemIndex, Vector3 aimPosition, NetworkObjectReference counterRef) {
    SabotageItemSO item = KitchenGameMultiplayer.Instance.GetSabotageItemFromIndex(itemIndex);
    if (item == null) return;

    bool hit = false;
    switch (item.targetType) {
        case TargetType.Player:
            // 复用现有的 OverlapSphere 逻辑
            Collider[] hits = Physics.OverlapSphere(aimPosition, 1.5f, playerLayerMask);
            foreach (var h in hits) {
                if (h.TryGetComponent(out Player target) && target != this) {
                    target.GetComponent<PlayerEffectHost>().ApplyEffect(
                        item.effectType, item.duration, myTeamId);
                    hit = true;
                }
            }
            break;
        case TargetType.Counter:
            if (counterRef.TryGet(out NetworkObject counterObj)) {
                var counterHost = counterObj.GetComponent<CounterEffectHost>();
                if (counterHost != null) {
                    counterHost.ApplyEffect(item.effectType, item.duration, myTeamId);
                    hit = true;
                }
            }
            break;
        case TargetType.Self:
            var selfHost = GetComponent<PlayerEffectHost>();
            selfHost.ClearAllPlayerEffects();
            selfHost.TriggerCleanWipeFlash();
            if (counterRef.TryGet(out NetworkObject counterObj2)) {
                var ch = counterObj2.GetComponent<CounterEffectHost>();
                ch?.ClearAllCounterEffects();
            }
            hit = true;
            break;
    }
}
```

**优点：** 不侵入现有的槽位逻辑，卡牌系统完全独立。
**缺点：** 和 `UseItemServerRpc` 有逻辑重复。

#### 方案 B：卡牌回写到槽位再触发

卡牌使用时，先 `Player.SetItemSlot(emptySlot, itemIndex)`，再调用现有的 `UseItemServerRpc`。

**优点：** 零代码重复，完全复用现有逻辑。
**缺点：** 卡牌系统耦合到槽位概念，且需要有空槽位才能使用。

**推荐方案 A**，因为卡牌系统在设计上就是要替代槽位系统作为道具使用入口。

### 3.5 关于 SO 的使用

**问：是否必须用 SO？**

在这个项目中，**是的，应该复用现有的 `SabotageItemSO`**，原因：

1. **数据已存在**：项目中已经创建了多个 `SabotageItemSO` 资产（.asset 文件），包含名称、效果、稀有度、图标等。新建一套数据结构意味着要重新维护两份。
2. **网络同步已就绪**：`SabotageItemListSO` 的索引机制已经用于 `NetworkVariable<int>` 同步，卡牌系统直接用 `itemIndex` 就能接入网络层。
3. **Inspector 可配置**：策划可以通过 SO 调整数值，不需要改代码。

**如何使用：**

- `TogglePanelUI` 通过 Inspector 引用 `SabotageItemListSO`（和 `KitchenGameMultiplayer` 一样）
- 创建卡牌时传入 `itemIndex`，通过 `sabotageItemListSO.GetFromIndex(itemIndex)` 获取 SO
- SO 数据传入 `EffectCardUI.SetCardData()` 填充 UI

### 3.6 完整数据流

```
1. 创建卡牌
   SabotageSystem / ItemBoxCounter / 测试按钮
       ↓ 传入 itemIndex
   TogglePanelUI.AddCard(itemIndex)
       ↓ sabotageItemListSO.GetFromIndex(itemIndex) → SabotageItemSO
       ↓ card.SetCardData(id, itemIndex, itemSO)
   EffectCardUI 展示 SO 数据（名称、图标、稀有度颜色）

2. 查询卡牌信息
   外部代码
       ↓ TogglePanelUI.Instance.GetAllCardInfos()
       ↓ 遍历 CardContainer，每张卡牌调 GetCardInfo()
   List<CardInfo> (包含 cardId + itemIndex + 效果数据)

3. 使用卡牌（拖拽消除）
   玩家拖拽卡牌向上超过阈值
       ↓ OnEndDrag 判断消除
       ↓ 通知 TogglePanelUI / Player 触发效果
   TogglePanelUI.UseCard(itemIndex, aimPosition, counterRef)
       ↓ Player.UseCardServerRpc(itemIndex, aimPosition, counterRef)
   服务器执行效果（复用现有的 ApplyEffect 逻辑）
       ↓ Destroy(cardGo)
```

## 五、开放问题

### 5.1 拖拽消除时如何获取瞄准目标？

- **TargetType.Player**: 需要 `GameInput.Instance.GetMouseWorldPosition()` 获取鼠标在地面平面上的世界坐标
- **TargetType.Counter**: 需要 `Player.selectedCounter` 引用
- **TargetType.Self**: 不需要目标
- 可在 `OnEndDrag` 时获取，传给 `UseCardServerRpc`

### 5.2 卡牌系统与现有物品栏是否共存？

- 如果共存：玩家可能从物品栏和卡牌两个入口使用同一道具，需要去重或选择
- 如果替代：卡牌系统接管所有道具发放和使用，物品栏退役
- **建议先共存，后续再决定**

### 5.3 拖拽消除的 UX 问题

- 向上拖拽消除与现有的 hover 上浮效果可能冲突（拖拽时 hover 已关闭，不会冲突）
- 消除后剩余卡牌立即收拢居中（现有 LayoutGroup 已自动处理）
