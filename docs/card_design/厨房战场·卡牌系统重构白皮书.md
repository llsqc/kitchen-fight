# 厨房战场·卡牌系统重构白皮书

> 从"破坏道具"到"策略卡牌"——一次彻底的数据、效果、网络三层重构

---

## 一、为什么必须重写

### 1.1 当前系统的症状

翻开 `SabotageItemSO.cs`，所有问题都源于一个文件：

```csharp
public enum EffectType {
    Stun, ReverseControls, LockCounter, CleanWipe,
}
```

这个枚举同时承担了三个职责：

| 职责 | 例子 | 问题 |
|---|---|---|
| 效果分类标签 | UI 上显示什么图标 | 加正面效果后枚举膨胀 |
| 执行逻辑分支 | `switch (effectType)` | 每加一个效果就要改 `ExecuteItemEffect` |
| 网络同步标识 | 通过索引传到服务端 | 枚举变动导致索引错位 |

更严重的是，`SabotageItemSO` 这个名字本身就带着"破坏道具"的基因——它无法优雅地容纳"加速移动"这种正面效果。

### 1.2 重写目标

| 目标 | 现状 | 重写后 |
|---|---|---|
| 支持正面效果 | 不支持 | 单人模式全是 Buff |
| 支持反制效果 | 不支持 | 多人模式有 Shield / Reflect |
| 效果强度可变 | 无 magnitude 字段 | 同一效果不同稀有度配不同数值 |
| 区分游戏模式 | 无 gameMode 字段 | Single / Multiplayer 分池 |
| 卡牌描述灵活 | 硬编码生成 | SO 自带 description，缺省时自动生成 |

## 二、数据层重构：从 SabotageItemSO 到 CardSO

### 2.1 新的枚举体系

```
GameMode        游戏模式      Single | Multiplayer
CardCategory    卡牌类别      Buff | Debuff | Counter
EffectType      效果类型      （见下文完整列表）
Rarity          稀有度        Common | Rare | Epic
TargetType      目标类型      Self | Player | Counter | Teammate
```

### 2.2 完整效果类型表

```
EffectType
├── 单人·Buff
│   ├── MoveSpeedUp          移动速度提升
│   ├── InteractionSpeedUp   交互速度提升
│   ├── DoubleScore          双倍得分
│   ├── ExtraTime            延长时间（即时）
│   ├── InstantComplete      瞬间完成（即时）
│   └── SelfClean             清除自身负面（即时）
│
├── 多人·Debuff（保留原有）
│   ├── Stun                 眩晕
│   ├── ReverseControls      反向操作
│   └── LockCounter          锁定台面
│
└── 多人·Counter（新增反制）
    ├── Shield                护盾：免疫下一次 Debuff
    └── Reflect               反弹：将下一次 Debuff 反弹给攻击者
```

### 2.3 CardSO 定义

```csharp
[CreateAssetMenu(fileName = "Card", menuName = "KitchenFight/Card")]
public class CardSO : ScriptableObject {
    // ── 身份信息 ──
    public string cardName;
    [TextArea] public string description;
    public Sprite icon;
    public Color placeholderColor = Color.white;

    // ── 分类标签 ──
    public GameMode gameMode;
    public CardCategory cardCategory;
    public Rarity rarity;

    // ── 执行参数 ──
    public EffectType effectType;
    public TargetType targetType;
    public float duration;      // 持续时间（秒），0 = 即时效果
    public float magnitude;     // 效果强度（1.5 = 1.5倍，2 = 翻倍，15 = 延长15秒）
}
```

### 2.4 CardListSO 定义

```csharp
[CreateAssetMenu(fileName = "CardList", menuName = "KitchenFight/CardList")]
```

## 三、效果执行架构

### 3.1 分流架构（按现状修订）

`Player.ExecuteItemEffect` 实际按 **targetType 一级分流**，Self 分支内再按 cardCategory / duration 二级分流：

```
UseCardServerRpc(itemIndex, aimPosition, counterRef)
  │
  ├── TargetType.Player（多人 Debuff）
  │     └── 瞄准点 OverlapSphere 命中玩家 → PlayerEffectHost.ApplyEffect(type, duration, sourceTeamId, sourceClientId)
  │
  ├── TargetType.Counter（LockCounter）
  │     └── counterRef → CounterEffectHost.ApplyEffect(...)
  │
  ├── TargetType.Teammate（多人 Buff）
  │     └── 瞄准点 OverlapSphere 命中的同队玩家（排除自己）→ PlayerEffectHost.ApplyBuff(...)
  │
  └── TargetType.Self
        │
        ├── cardCategory == Counter → ApplyCounter（仅 Shield / Reflect 有效）
        ├── duration > 0（持续 Buff）→ ApplyBuff
        └── duration == 0（即时）→ switch effectType
              ├── ExtraTime        → KitchenGameManager.AddGameTime(magnitude)
              ├── InstantComplete  → CuttingCounter / StoveCounter.InstantComplete()
              └── SelfClean/CleanWipe → ClearAllPlayerEffects + 净化闪光 + 清除选中柜台效果
```

> ⚠️ 已知问题：category=Counter 的卡会先走 `ApplyCounter`，而该方法只处理 Shield/Reflect——多人净化卡 CleanWipe（category=Counter）因此成为死卡，见 TODO-1。

### 3.2 效果施加接口（按现状修订）

实际落地为三个独立方法，而非单一签名扩展：

```csharp
// Debuff 施加入口（含 Shield/Reflect 拦截链）
void ApplyEffect(EffectType type, float duration, int sourceTeamId, ulong sourceClientId)

// Buff 施加（不经过拦截链，直接设置计时器）
void ApplyBuff(EffectType type, float duration, float magnitude)

// Counter 防御状态（仅处理 Shield / Reflect）
void ApplyCounter(EffectType type, float duration, float magnitude)
```

magnitude 仅存在于 Buff / Counter 路径；Debuff 的 ApplyEffect 不接收 magnitude。

## 四、PlayerEffectHost 重构

### 4.1 当前状态

```
PlayerEffectHost
├── stunTimer          负面
├── reverseTimer       负面
├── recentVictimTimer  被动减半保护
└── cleanWipeFlash     净化闪光
```

### 4.2 重构后

```
PlayerEffectHost
│
├── 负面效果计时器（可被拦截/反弹）
│   ├── stunTimer
│   └── reverseTimer
│
├── 正面效果计时器（Buff，不可被拦截）
│   ├── moveSpeedTimer + moveSpeedMagnitude
│   ├── interactionSpeedTimer + interactionSpeedMagnitude
│   └── doubleScoreTimer + doubleScoreMagnitude
│
├── 防御状态计时器（Counter）
│   ├── shieldTimer + shieldCharges    ← 护盾，拦截 Debuff
│   └── reflectTimer + reflectCharges ← 反弹，反弹 Debuff 给攻击者
│
└── 辅助状态（保留）
    ├── recentVictimTimer              ← 被动减半保护（保留）
    └── cleanWipeFlash                 ← 净化闪光视觉
```

### 4.3 ApplyEffect 入口逻辑（拦截链，按现状修订）

拦截条件是 `IsPlayerStateEffect(type)`（当前仅 Stun / ReverseControls），**不是按 CardCategory 判断**；Buff 走独立的 `ApplyBuff`，不进入拦截链：

```
ApplyEffect(type, duration, sourceTeamId, sourceClientId):
  │
  ├── IsPlayerStateEffect(type)?  // 仅 Stun / ReverseControls
  │     │
  │     ├── shieldCharges > 0 ?
  │     │     是 → 消耗 1 次护盾，return（效果被吞掉）
  │     │
  │     └── reflectCharges > 0 ?
  │           是 → 消耗 1 次反弹，对 sourceClientId 的 Player
  │                调 ApplyEffectDirect（绕过拦截链），return
  │
  └── ApplyEffectDirect(type, duration, sourceTeamId):
        │
        ├── IsPlayerStateEffect && recentVictimTimer > 0 ?
        │     是 → duration *= 0.5，并重置 10s 保护窗口
        │
        └── 设置 stunTimer / reverseTimer（取较大值刷新）
```

`ApplyBuff`（正面效果）：按 duration 取较大值刷新计时器并记录 magnitude，无任何拦截。

## 五、反制系统详解

### 5.1 净化（SelfClean）—— 事后补救

**场景：** 你被眩晕了，动不了，打出净化卡 → 立即解除。

**机制：**
- `ClearAllPlayerEffects()` — 把 stunTimer / reverseTimer 归零
- 已有代码，不需要改动
- 即时效果，无持续时间

> ⚠️ 现状：单人的「清除疲劳」（SelfClean / Buff）正常生效；多人的 CleanWipe 卡因 category 误配为 Counter 而成为死卡（TODO-1）。

### 5.2 护盾（Shield）—— 事前预防

**场景：** 你预判对手要干扰你，提前打护盾 → 下一个 Debuff 被完全吞掉。

**机制：**
- 新增 `shieldTimer`（NetworkVariable\<float\>）+ `shieldCharges`（NetworkVariable\<int\>）
- 打出护盾卡时：`shieldTimer = duration`，`shieldCharges = RoundToInt(magnitude)`（最小 1；当前护盾.asset：magnitude=1、duration=5）
- 收到 Debuff 时：`shieldCharges > 0` → 消耗 1 次，效果不生效
- 护盾到期或次数用完自动消失

**与现有减半保护的区别：**

| 对比 | 减半保护 (recentVictimTimer) | 护盾 (Shield) |
|---|---|---|
| 触发方式 | 被动，被打后自动触发 | 主动，打牌触发 |
| 效果 | 持续时间减半 | 完全免疫 |
| 持续 | 10 秒 | 卡牌配置的 duration |
| 策略性 | 低（自动的） | 高（玩家选择时机） |

### 5.3 反弹（Reflect）—— 以牙还牙

**场景：** 对手对你丢眩晕，你有反弹 → 眩晕反弹到对手身上，你不受影响。

**机制：**
- 新增 `reflectTimer`（NetworkVariable\<float\>）+ `reflectCharges`（NetworkVariable\<int\>）
- 打出反弹卡时：`reflectTimer = duration`，`reflectCharges = 1`
- 收到 Debuff 时：`reflectCharges > 0` → 消耗 1 次
  - 找到 `sourceClientId` 对应的 Player
  - 对该 Player 调用 `ApplyEffect`（绕过拦截链，直接生效）
  - 自己不受影响

**难点与解决：**
- `ApplyEffect` 当前只接收 `sourceTeamId`，不知道具体是谁攻击的
- 扩展签名增加 `sourceClientId`
- `Player.UseCardServerRpc` 调用时传入自己的 `OwnerClientId`

## 六、稀有度设计

### 6.1 发牌概率（已有）

```
Common  60%
Rare    30%
Epic    10%
```

### 6.2 效果强度梯度（新增）

同一个 EffectType，不同稀有度配不同的 duration 或 magnitude。这意味着同一个效果会有 3 张卡牌（Common/Rare/Epic 各一张）。

**示例 — 加速移动：**

| 稀有度 | magnitude | duration |
|---|---|---|
| Common | 1.3 | 8s |
| Rare | 1.5 | 10s |
| Epic | 1.8 | 12s |

**示例 — 护盾：**

| 稀有度 | charges | duration |
|---|---|---|
| Common | 1 次 | 5s |
| Rare | 1 次 | 8s |
| Epic | 2 次 | 8s |

这只是数据配置，不需要代码改动——策划在 `.asset` 文件里填不同的数值即可。

> 现状：当前 15 张卡中每种效果仅 1 张，未配置稀有度变体（TODO-7）。

## 十一、已知问题与 TODO（20260815 审查）

> 以下为 2026-08-15 对 15 张已配置卡牌（`Assets/ScriptableObjects/Cards/`）与代码实现的审查结论。正文已按实现现状修订，此处归档待办事项。

### TODO-1 死卡修复（高优先级）

多人净化卡 `CleanWipe.asset`（cardCategory=Counter，effectType=CleanWipe）经 `Player.ExecuteItemEffect` 的 Self 分支路由到 `PlayerEffectHost.ApplyCounter`，而该方法只处理 Shield/Reflect，**打出后无任何效果**。

修复方案（二选一）：
- A（推荐）：.asset 改为 `cardCategory=Buff` + `effectType=SelfClean`，与单人「清除疲劳」一致，零代码改动
- B：`ExecuteItemEffect` Self 分支先按 effectType 判断即时净化效果，再判 Counter

### TODO-2 稀有度平衡

Stun（2s，Rare）与 LockCounter（15s，Common）强度倒挂。建议调整数值或稀有度标注。

### TODO-3 补偿卡池过滤

`CardDealer.PickCompensationCardIndex` 仅按模式+稀有度过滤，落后方可能抽到 Reflect/护盾等防御卡，翻盘价值低。建议对补偿路径增加 `CardCategory.Buff` 过滤。

### TODO-4 开局发牌不同步

`TogglePanelUI.Player_OnSpawned` 在客户端本地 `AddCard` 5 张，服务器不感知；与落后补偿的 `Player.AddCardClientRpc`（服务器权威）路径不一致。建议统一为服务器发牌。

### TODO-5 多人 Buff 卡无法自用

`TargetType.Teammate` 分支排除施放者自身（`teammate == this → continue`），多人模式无法给自己上 Buff（单人因 targetType=Self 不受影响）。需设计决策：允许自用（代码改动）或定稿为仅队友（本文档 §7.2 已按现状表述）。
